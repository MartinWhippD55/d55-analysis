- **What:** section variant CRUD handlers (order, default)
- **Why:** Variants let one section slot render different layouts depending on contract data without duplicating whole templates. These handlers persist the variant set, its evaluation order and its default — exactly the state the render pipeline (US-06) reads to do first-match-wins selection, and that the frontend `SectionVariantsComponent` (US-09) manages. Variant rules (US-04-3) attach to the records this handler owns.
- **Done when:**
  - `list/add/reorder/update/delete-section-variant` handlers are implemented against the design's route table (`GET/POST /contract-note-sections/{id}/variants`, `PUT /contract-note-sections/{id}/variants/reorder`, `PUT/DELETE /contract-note-sections/{id}/variants/{variantId}`).
  - Variant records are written under `PK = SECTION#{sectionId}`, `SK = VARIANT#{variantOrder}#{variantId}` with `variantId`, `name`, `variantOrder`, `isDefault`, `schemaS3Key` and optional `specification`.
  - At most one variant may be `isDefault`; a request that would create a second default is rejected with HTTP 400 (parent 19.3).
  - Evaluation order is persisted via `variantOrder`; `reorder` updates it and `list` returns variants in evaluation order (parent 19.4).
  - Each variant is versioned independently — version history is keyed `{sectionId}#{variantId}` (parent 19.1).
  - A section with no variant records is treated as a single implicit variant using the section's own `schemaS3Key`, preserving existing behaviour (Property 36, parent 19.8).
  - A missing section or variant returns a 404 not-found error.

### Suggested approach

```typescript
// GET /contract-note-sections/{id}/variants -> variants in evaluation order.
// Item shape matches the SectionVariant interface (shared-lib:types, US-01):
// [
//   { "variantId": "var-1", "name": "SME layout", "variantOrder": 0,
//     "isDefault": false, "schemaS3Key": "sec-123/var-1/schema.json",
//     "specification": { "type": "EQUALS", "field": "offer.producttype", "value": "Fixed" } },
//   { "variantId": "var-2", "name": "Default", "variantOrder": 1,
//     "isDefault": true, "schemaS3Key": "sec-123/var-2/schema.json" }
// ]

export const listSectionVariants: Handler = async (event) => {
  const { id: sectionId } = event.pathParameters;
  // Query PK = SECTION#{sectionId}, SK begins_with VARIANT# — sorted by variantOrder.
  const variants = await queryVariants(sectionId);
  return ok(variants); // already in evaluation order via SK
};

export const addSectionVariant: Handler = async (event) => {
  const { id: sectionId } = event.pathParameters;
  const { name, isDefault = false, specification } = JSON.parse(event.body);
  if (isDefault && (await hasDefaultVariant(sectionId))) {
    return badRequest('A section may have at most one default variant'); // parent 19.3
  }
  const variantId = randomUUID();
  const variantOrder = await nextVariantOrder(sectionId); // append to end
  await putVariant({
    PK: `SECTION#${sectionId}`,
    SK: `VARIANT#${variantOrder}#${variantId}`,
    variantId, name, variantOrder, isDefault,
    schemaS3Key: `${sectionId}/${variantId}/schema.json`,
    specification, // absent for the default variant
  });
  return created({ variantId });
};

// reorderSectionVariants: rewrite variantOrder / SK for the supplied variantId order.
// updateSectionVariant: patch name/isDefault (re-check at-most-one-default on isDefault=true).
// deleteSectionVariant: remove the VARIANT# record and its {sectionId}#{variantId} history.
```
