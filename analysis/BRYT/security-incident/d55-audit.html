What "odd" looks like

  • Activity from new source IPs or geographies / ASNs.
  • Actions in regions D55 doesn't use.
  • New IAM users, keys, or login profiles — persistence.
  • Logging/GuardDuty being disabled — evasion.
  • Secrets / snapshots / AMIs read or shared out — exfil.
  • New EC2 instances (esp. large/GPU) — cryptomining.
  • Off-hours bursts of Describe/List — recon.

Running the sweep

The same read-only collector audit-aws.ps1 loops each profile and region, pulls the checks below, tabulates them, and writes a flagged 00-SUMMARY.txt plus per-account output folders. Invoked with the call operator (not -File) so the comma-separated -Profiles / -Identities lists bind as arrays.

& .\audit-aws.ps1 `
    -Profiles d55-inv-audit,d55-inv-orchestration,d55-inv-wafr,`
              d55-inv-sagemaker-v2,d55-inv-service-catalog `
    -Identities rhys.jacob@d55.co.uk,rhys.jacob+unified-engineer@d55.co.uk `
    -Days 50 `
    -Prefix d55
Read-only by construction: the script calls only sts:GetCallerIdentity, cloudtrail:LookupEvents, iam:Get*/List*/GenerateCredentialReport, guardduty:List*/Get*, and ec2:Describe*. It modifies nothing.

Findings

Results of the sweep of the five d55-inv-* accounts for activity by the Rhys identity, from the 17 Sep 2026 run over the 30 Jul–17 Sep window.

Headline No evidence of compromise — one item to confirm

Four of the five accounts (d55-inv-audit, d55-inv-orchestration, d55-inv-wafr, d55-inv-service-catalog) show no Rhys activity at all in the window. The fifth, d55-inv-sagemaker-v2, is active and raised the run's single flag: 47 high-signal events. On inspection those are a routine SageMaker/DataZone environment deploy via CloudFormation on 14 Aug, not attacker behaviour.

There is no log-tampering/evasion (StopLogging/DeleteTrail), no new IAM users or access keys, no EC2 launches or new key pairs, and no high-signal activity by any other actor across the five accounts. The one item to confirm is two source IPs on the sagemaker-v2 account that we have not yet positively tied to Rhys.

Read this correctly: a clean management-event trail is reassuring but not a full exoneration — it does not cover S3 object-level reads or anything older than 90 days. See Limitations and Next Steps.

Secondary finding — GuardDuty coverage gap detection

As in the Bryt sweep, GuardDuty reported no detector across the accounts/regions checked — a detection gap that fits the incident's “ran undetected” root cause. Enabling GuardDuty org-wide is already a tracked hardening action.

Confirm this is a genuine absence and not the read-only audit role lacking guardduty:ListDetectors; where a region wrote no file, a detector may exist there with no in-window findings.

Limitations

What this sweep can and cannot see — read before drawing an all-clear.

  • 90-day horizon. cloudtrail:LookupEvents only reaches back 90 days. If malware landed earlier, the start is invisible here — use an archived trail / CloudTrail Lake / Athena over the S3 log bucket.
  • Management events only. Bulk S3 GetObject and other data-plane reads are not returned unless data events are enabled on a trail.
  • Per-account, per-region. Coverage is only as complete as the profiles and regions supplied. This pass covered five d55-inv-* profiles and three regions; off-scope accounts/regions can hide activity — use -AllRegions for a full sweep.
  • Identity matching. SSO role-session names must match the -Identity string; if it's formatted unexpectedly, events can be missed. Cross-check against the raw pull.
  • Clean ≠ exonerated. A quiet CloudTrail is reassuring but doesn't rule out data-event exfil or pre-window actions.
Strengthen it: if an org trail with data events or CloudTrail Lake exists, we can query the full period and object-level access directly — tell us what's available and we'll add those queries.
