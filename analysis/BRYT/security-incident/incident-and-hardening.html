Initial Access — Malicious Repo / Untrusted Code

How the attacker got in: a social-engineering + malicious-code supply attack, not a GitHub or infrastructure weakness. The lure exploited the one thing developers do reflexively — clone and run unfamiliar code on their main machine.

What happened

Lure
Rhys was contacted by a "company" offering consultancy work.
Payload delivery
They supplied a repository to clone.
Execution
Malware installed when the project was set up / run locally, then harvested the credential chain.
Known campaign pattern: fake recruiters / consultancy offers / "coding challenges" / "review our repo" handing developers a booby-trapped project is an active, well-documented attack. Developers are the specific target. Brief the team on this — blamelessly — as a concrete example.

The technical clarification that shapes the fix

A plain git clone does not execute hooks from the remote — .git/hooks/ is created fresh locally, so committed hook files aren't copied in or run. The malware almost certainly fired when the repo was used after cloning. Realistic triggers:

  • npm/yarn/pip install running preinstall/postinstall lifecycle scripts — by far the most common.
  • Opening in an IDE that auto-runs tasks, extensions, or a devcontainer.
  • Building / running it (make, a run script, "just run this to see it work").
  • A .gitattributes clean/smudge filter or configured core.hooksPath (needs a config/setup step, usually paired with "run our setup script").
So the fix isn't "block git hooks" — it's never let untrusted code execute in an environment that holds your credentials. Regardless of the exact trigger, the controls below apply.

Layered prevention

  • Written policy: unsolicited external code is never cloned or run on a work machine. Full stop.
  • Independently verify the company/contact before any engagement — real domain, real people, out-of-band confirmation. These lures use plausible but fake companies.
  • Named awareness training on this exact scenario: fake recruiters/consultancy, coding challenges, "review my PR".

Even if malicious code runs, it should find nothing worth stealing and no way out.

  • Throwaway VM / ephemeral cloud sandbox (or locked-down container/devcontainer) with no credential chain: no ~/.aws, no SSH keys, no logged-in sessions, no browser profiles, no PATs.
  • Restrict network egress so malware can't phone home or exfiltrate.
  • Destroy it after. Never evaluate unknown repos on the machine that holds your keys.
  • Disable install scripts by default: npm ignore-scripts=true globally / npm install --ignore-scripts; consider pnpm's explicit build-script allowlist.
  • IDE Workspace Trust (VS Code & equivalents) so opening a folder doesn't auto-run tasks/extensions — don't disable it "for convenience".
  • Inspect before executing: read package.json scripts, look for obfuscated/base64 blobs and suspicious postinstall/setup steps.
  • For deliberate clones of untrusted repos: avoid --recurse-submodules, and don't run any "setup" script they provide.
  • If the machine holds no long-lived keys/PATs at rest — only short-lived, on-demand creds — the malware has little or nothing to harvest.
  • Same control as the Identity Center / short-lived-creds work; it doubles as prevention-of-spread and containment.
  • Behavioral EDR should flag "install script spawns a shell that reads credential stores and beacons out".
  • Egress filtering/monitoring on dev machines catches the phone-home. See the Detection & Monitoring tab.

Safe-evaluation checklist — when someone hands you a repo

#Before you touch it
1Verify the requester independently (domain, people, out-of-band). Unsolicited? Default to no.
2Clone only into a disposable VM/sandbox with zero credentials and restricted egress.
3Do not run install/build/setup. Read package.json scripts + look for obfuscated code first.
4Install with --ignore-scripts; open with Workspace Trust off / untrusted.
5If anything must run, keep it in the sandbox, watch egress, and destroy the environment after.
6Never bring the repo onto your primary machine or one holding keys/sessions.
One-line version: the attack works because developers run untrusted code on trusted machines. Sandbox the code or strip the machine of credentials — either half breaks it; do both.

Response Plan

In order. Contain first, investigate second, remediate third — don't clean repos before the identity is contained, or the attacker re-compromises during cleanup.

1

Isolate the machine — don't wipe yet

Pull it off the network. Preserve for forensics (disk image / memory capture) if possible — the malware's start date scopes everything else. Stop using it; don't authenticate to anything from it.

2

Contain the identity everywhere

Rhys is a compromised identity, not just a GitHub login. From a clean machine: reset password; revoke all GitHub PATs / SSH keys / OAuth apps / sessions; reset 2FA. Revoke SSO/IdP sessions (session cookies survive password resets). Deactivate AWS keys and invalidate active STS sessions.

3

Rotate everything in the blast radius

Not just the traced token: all AWS keys/roles reachable (incl. AKIA4TNB…), the ghp_… PAT, SSH keys, npm/PyPI/registry tokens, CI secrets, .env values, and DB creds. Rotate the underlying Secrets Manager secrets (centrestage / phidex) too.

4

Hunt — build the attacker timeline

GitHub org audit log (pushes, force-pushes, new tokens, member/permission/webhook changes). AWS CloudTrail (key usage, new IAM users/keys, unusual regions, data access). IdP sign-in logs (impossible-travel, new devices). Correlate against the malware start date.

5

Find persistence & lateral movement

Look for planted backdoors: new IAM users/keys/roles, new GitHub org members / deploy keys / machine users / Apps, new authorized_keys on reachable servers, new OAuth grants or mail-forwarding rules.

6

Recover clean repo history

From a verified-clean local clone (pre-compromise reflog), reset --hard <known-good-sha>, preserve malicious commits as evidence first, then push --force-with-lease per affected branch/tag. Temporarily allow force-push, re-lock immediately after.

7

Rebuild the endpoint

Flatten and reinstall from known-good media once forensics is done. Restore data selectively (scanned). Issue fresh credentials to Rhys on the rebuilt machine — never reuse the old ones.

Hardening — Best Practice

Grouped by the gaps this incident exposed. The three highest-impact for this incident: secret scanning + push protection, short-lived credentials over long-lived keys/PATs, and EDR on the endpoint.

  • No plaintext secrets in code, ever — use a secrets manager (Secrets Manager / SSM), as the DMS code already does well.
  • Secret scanning + push protection — GitHub Advanced Security, or gitleaks/trufflehog in pre-commit hooks and CI. This is what would have caught every secret we found.
  • Prefer short-lived, auto-rotated credentials over long-lived keys/PATs.
  • Purge historical leaks (git filter-repo/BFG) — but remember scrubbing is not remediation; rotation is.
Why here: the AWS key, PAT, and password literals were all committable because nothing scanned content on the way in.
  • Enforce SSO + phishing-resistant MFA (passkeys / hardware keys) org-wide.
  • Least privilege everywhere; scope IAM roles/tokens tightly (see Identity Center tab).
  • Drop long-lived AWS keys for SSO / short-lived STS roles; use OIDC for CI instead of stored cloud keys.
  • Fine-grained, expiring PATs (or GitHub Apps) instead of classic long-lived tokens.
Why here: standing admin + long-lived creds on the endpoint gave a stolen token full, lasting reach.
  • Branch protection: block force-pushes, require PR review + status checks on protected branches.
  • Require signed commits + protected tags — addresses the impersonation/tamper vector.
  • CODEOWNERS-gated reviews; restrict who can change CI/CD workflows.
Why here: history was rewritten & force-pushed; these controls block or expose exactly that.
  • EDR on all developer machines with alerting.
  • Full-disk encryption, encrypted SSH keys, patched OS/tooling.
  • Don't store long-lived creds on disk; use OS keychain + short-lived tokens.
Why here: the root cause was a persistent, undetected endpoint compromise harvesting the credential chain.
  • OIDC federation for deployments — no stored cloud creds in CI.
  • Pin dependencies, use lockfiles, review install hooks; scan dependencies (Dependabot / audit).
  • Isolate & least-privilege CI runners; scope CI secrets per-environment.
  • Centralize & monitor audit logs (GitHub audit log, CloudTrail, IdP sign-ins) with anomaly alerts.
  • Maintain offline / immutable backups, including repo mirrors.
  • Written incident-response runbook; rehearse credential rotation.

AWS Identity Center — Least-Privilege Model

Moving devs off standing Administrator for convenience to read-only daily access + assume-role for deploys. This is the accepted pattern and directly shrinks the blast radius a stolen session can cause.

The core model

  • Permission sets mapped to groups, not individuals — put people in IdP groups, assign permission sets to groups.
  • Read-only as the daily default — most devs only need to look; a compromised read-only session can't mutate anything.
  • Deploys go through CI/CD, not humans — pipeline authenticates via OIDC, humans review/approve. Most devs never need local deploy rights.

Where CDK roles fit — the key insight

cdk bootstrap creates roles in each account. The heavy IAM privilege lives in the CloudFormation execution role, which only CloudFormation uses — not the human.

  • cdk-hnb659fds-deploy-role-* — CDK assumes this to orchestrate.
  • cdk-hnb659fds-cfn-exec-role-* — CloudFormation assumes this to create resources (the real power).
  • cdk-hnb659fds-file/image-publishing-role-* — asset uploads to S3/ECR.
  • cdk-hnb659fds-lookup-role-* — read-only context lookups.

So a "deployer" permission set only needs sts:AssumeRole on the cdk-* roles:

{
  "Effect": "Allow",
  "Action": "sts:AssumeRole",
  "Resource": "arn:aws:iam::*:role/cdk-hnb659fds-*"
}
Tighten the cfn-exec-role policy at bootstrap via --cloudformation-execution-policies rather than leaving the default AdministratorAccess.

Guardrails to layer on

  • Just-in-time elevation — grant deploy/admin on request for a limited window, not standing.
  • Short session durations on privileged sets (e.g. 1h) so stolen tokens expire fast.
  • Require MFA in Identity Center, ideally phishing-resistant.
  • Environment separation — prod deploy pipeline-only; devs get Deployer in dev/uat, not prod.
  • SCPs as an org backstop — deny disabling CloudTrail/GuardDuty, deny unused regions.
Impact on this incident: under this model a stolen dev session is read-only — it can't create IAM users, spin up resources, or tamper with infra. The privileged path needs an explicit, short-lived, audited assume-role the malware's harvested standing token wouldn't hold.

Detection & Monitoring

The most damning fact of this incident is that it ran "for some time" undetected — the compromise wasn't stealthy, it was unwatched. The goal isn't one magic alert; it's layered detection across the attack chain so it's caught at some stage even if the first is missed.

Framing: this attack was loud at several stages — credential-store access, force-push, likely new IAM keys, possibly data pulls. Detection failed because nothing was listening at any of them. The metric to drive down is MTTD (mean time to detect): from "some time" to "hours".

Signals by layer of the attack chain

Where it started, and where there was zero visibility.

  • EDR with behavioral detection (not just signature AV) — alert on a process reading ~/.aws/credentials, the Git credential store, ~/.ssh, or browser cookie DBs.
  • Unusual persistence — new scheduled tasks / services / registry run-keys.
  • Beaconing / anomalous outbound network patterns.
  • Endpoint honeytoken — a decoy AKIA… in ~/.aws/credentials or a fake .env. Any use = high-fidelity "creds compromised" alert.
  • Impossible-travel / new-ASN / new-device sign-in alerts from the IdP.
  • Alert on new MFA method registered, MFA reset, or auth from residential-proxy / hosting-provider IPs.
  • Watch session usage, not just logins — stolen session cookies bypass MFA, so a session token appearing from a new geography is the tell.
  • Stream the org audit log to a SIEM; alert on force-push to protected/default branches, pushes with history rewrites/deletions.
  • Alert on new PAT or SSH key created, new OAuth/App authorization, member/permission changes, webhook changes.
  • Secret scanning + push protection alerts routed to a watched channel — this is what would have flagged the AKIA/ghp_ secrets years ago (private repos need GHAS).
  • Alert on CI/CD workflow file changes (.github/workflows, deploy YAML) and on commits that lose signatures once signing is required.
  • GuardDuty — detects credential exfil/use anomalies, e.g. UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration, anomalous API calls, use from new regions, recon patterns.
  • CloudTrail alerting on high-signal events: CreateUser, CreateAccessKey, AttachUserPolicy, CreateLoginProfile (persistence); StopLogging / DeleteTrail (evasion); IAM changes outside the pipeline.
  • Data-exfil detection — GuardDuty S3 protection; alert on unusual bulk GetObject from the DMS output buckets or access from unfamiliar principals.
  • AWS honeytoken IAM key — a deliberately-planted, unused key; any use = alarm.
  • Billing anomaly alerts — blunt but effective backstop for cryptomining / abuse.

Force-multipliers

Honeytokens / canaries highest ROI

Plant fake credentials across endpoints, repos, S3 buckets, and Secrets Manager. They flip the economics — an attacker can't tell real from fake, and a single trigger is unambiguous.

  • Free: canarytokens.org; managed: Thinkst Canary.
  • The single highest-value detection for the exact "stolen creds get used" moment.

Centralize & correlate (SIEM / log lake)

Individual signals are noisy; the power is correlation. "EDR alert + GitHub force-push + CloudTrail CreateAccessKey in the same window" is a near-certain incident.

  • Feed GitHub audit log, CloudTrail, GuardDuty, and IdP logs into one place.
  • Alert on the rare/irreversible, not the routine — force-push to main, new IAM key, MFA reset, CloudTrail disabled.

The bits people skip

  • Log retention > dwell time — if you keep 90 days and malware sat for six months, both detection and investigation fail. Retain audit/CloudTrail long enough to see the start.
  • Route alerts to somewhere staffed — an alert nobody reads isn't detection. Define who triages and an SLA.
  • Track MTTD and run purple-team tests — drop a canary, force-push to a test protected branch, confirm alerts actually fire.
  • Baseline "normal" — normal regions, deploy identities, working hours — so anomalies mean something.
