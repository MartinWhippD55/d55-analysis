Tech & Areas — ELI5

What we're skilling up on

ELI5: Azure is Microsoft's cloud — the equivalent of AWS. It's where you rent compute, storage, databases, networking, and identity instead of running your own servers. You organise everything under a tenant (the company's identity boundary), subscriptions (billing/isolation), and resource groups (folders for related resources). Identity is handled by Microsoft Entra ID (formerly Azure AD).

Why it matters here

  • Contollo runs on Microsoft/Azure, so everything we deploy — agents, data, dashboards — lands here.
  • Their single Microsoft 365 tenancy and Entra ID are the backbone; our agent identities and permissions live in Entra.
  • Cost, region (EU data residency), and networking choices all flow from Azure fundamentals.
Bridge: If you know AWS, most concepts map 1:1 — accounts→subscriptions, IAM→Entra ID, S3→Blob Storage, Lambda→Functions, ECS/Fargate→Container Apps.

Further reading

  • Microsoft Entra ID fundamentals
Which subscriptions/regions does Contollo use? Who administers the tenant today (the MSP being replaced)? What access will D55 get, and how (Entra guest, PIM roles)?
ELI5: MAF is Microsoft's open-source SDK + runtime for building AI agents and multi-agent workflows, in .NET and Python. It unifies Microsoft's two earlier frameworks — Semantic Kernel and AutoGen — into one supported platform. You get a clean programming model: chat clients (talk to a model), tools (functions the agent can call), MCP integrations (plug in external tools), context providers (memory), middleware (intercept steps), and workflows (graph-based orchestration of several agents/steps).

Why it matters here

  • This is the framework Contollo wants their agentic workflows written in — including the CMAP "doing" and "analyst" agents.
  • MAF hit 1.0 GA on 2 April 2026, so it's production-ready but still young — expect docs and patterns to keep moving.
  • It's the thing our team most needs hands-on reps with; conceptually it's close to what we already build.
Bridge: A MAF tool is the same idea as a Claude/Copilot skill or tool; MAF speaks MCP, so MCP servers we've already written can be reused as agent tools with little change.

Further reading

  • Agent Framework overview (Microsoft Learn)
  • Introducing MAF (dev blog)
  • If you know AutoGen/SK: migration guide
.NET or Python for Contollo's agents? (Team's agentic experience likely leans Python/TS.) Which MAF version/patterns does the scoped work assume?
ELI5: Foundry is the Azure home for AI. The model catalog lets you pick a model; the Foundry Agent Service is a managed runtime that hosts and scales agents for you — each agent session runs in an isolated sandbox with its own Entra identity and built-in tracing. Think of MAF as how you write the agent, and Foundry as where you run, govern, and observe it. The portal lives at ai.azure.com.

Why it matters here

  • It's the natural place to deploy MAF agents on Azure with identity, observability, and scaling handled.
  • Agents can be published into Microsoft Teams and M365 Copilot — where Contollo's staff already work.
  • Built-in OpenTelemetry tracing and evaluations help with the governance the Semanti report says is pending.
Bridge: Foundry Agent Service is "bring your own framework + model" and is built on the OpenAI Responses API — the same agentic wire protocol many of us already build against.

Further reading

The Microsoft data & governance layer

ELI5: Purview is Microsoft's data governance, security, and compliance suite. It does two big things: data governance (catalog, classify, and map where data lives and flows) and data protection/compliance (sensitivity labels, DLP to stop data leaking, retention, insider-risk and audit). It's how you answer "what sensitive data do we have, who can touch it, and can we prove it?"

Why it matters here

  • The Semanti report flags shadow-AI data leakage and pending governance as a top risk — Purview is the tool that addresses it.
  • Client-confidential drawings, cost data, and PII need labelling/DLP before agents process them at scale.
  • Directly supports the "acceptable-use + approved-tools + Copilot guardrails" work the report says is outstanding.

Further reading

  • Microsoft Purview overview
  • Purview for AI / Copilot governance
Is Purview licensed/enabled in their tenant today? Are sensitivity labels and DLP already in use, or greenfield? This shapes what agents are allowed to read.
ELI5: Power BI is Microsoft's dashboarding/reporting tool — connect data, build visuals, share reports. Microsoft Fabric is the broader data platform underneath it (a "one-stop" for data engineering, warehousing, and a shared storage layer called OneLake). Power BI is now part of Fabric. How we might integrate agentic workflows

Four broad routes, roughly in order of directness. The right mix depends on what CMap's API actually allows and what data we're allowed to touch.

  • 1. Direct CMAP API (ideal for agents). If CMap exposes a documented REST API, the "analyst" agent reads (projects, timesheets, utilisation) and the "doing" agent writes (updates, entries) via tools that wrap those endpoints. Cleanest fit for MAF.
  • 2. CMAP MCP server. If CMap (or we) can expose an MCP server over the API, it plugs straight into MAF as a tool set — and lines up exactly with the report's "API/MCP support" wording and our existing MCP experience.
  • 3. Via the Microsoft layer. Where CMap already syncs to Business Central, Power BI, or SQL Server, the analyst agent can read from those instead of CMap directly — often the fastest path to insight without write access.
  • 4. Native connectors for plumbing. Use CMap's built-in connectors for bulk/scheduled data movement (e.g. into Power BI/Fabric) and reserve agent calls for the interactive/decision parts.
Bridge: Routes 1 and 2 are exactly the kind of "wrap an API as tools / stand up an MCP server" work D55 already does well — the new part is the Azure hosting and Contollo's data governance around it.

The "doing" + "analyst" split (from the report)

Analyst agent (read)

  • Answers "how's this project / my utilisation / this month tracking?"
  • Read-only — lower risk, natural first build.
  • Can lean on Power BI / Business Central data if direct CMAP read is limited.

Doing agent (write)

  • Performs updates — timesheet nudges, status/entry updates.
  • Needs write scopes + human-in-the-loop confirmation.
  • Higher risk; sequence it after the analyst agent proves the API.
