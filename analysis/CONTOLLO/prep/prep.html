Tech & Areas — ELI5

Plain-English overview of each technology, why it matters for Contollo, and links for further reading. Green "bridge" notes connect the new thing to something the team already knows. Expand a section to read more.

What we're skilling up on

ELI5: Azure is Microsoft's cloud — the equivalent of AWS. It's where you rent compute, storage, databases, networking, and identity instead of running your own servers. You organise everything under a tenant (the company's identity boundary), subscriptions (billing/isolation), and resource groups (folders for related resources). Identity is handled by Microsoft Entra ID (formerly Azure AD).

Why it matters here

  • Contollo runs on Microsoft/Azure, so everything we deploy — agents, data, dashboards — lands here.
  • Their single Microsoft 365 tenancy and Entra ID are the backbone; our agent identities and permissions live in Entra.
  • Cost, region (EU data residency), and networking choices all flow from Azure fundamentals.
Bridge: If you know AWS, most concepts map 1:1 — accounts→subscriptions, IAM→Entra ID, S3→Blob Storage, Lambda→Functions, ECS/Fargate→Container Apps.

Further reading

  • Azure Cloud Adoption Framework
  • AZ-900 Azure Fundamentals
  • Microsoft Entra ID fundamentals
Which subscriptions/regions does Contollo use? Who administers the tenant today (the MSP being replaced)? What access will D55 get, and how (Entra guest, PIM roles)?
ELI5: MAF is Microsoft's open-source SDK + runtime for building AI agents and multi-agent workflows, in .NET and Python. It unifies Microsoft's two earlier frameworks — Semantic Kernel and AutoGen — into one supported platform. You get a clean programming model: chat clients (talk to a model), tools (functions the agent can call), MCP integrations (plug in external tools), context providers (memory), middleware (intercept steps), and workflows (graph-based orchestration of several agents/steps).

Why it matters here

  • This is the framework Contollo wants their agentic workflows written in — including the CMAP "doing" and "analyst" agents.
  • MAF hit 1.0 GA on 2 April 2026, so it's production-ready but still young — expect docs and patterns to keep moving.
  • It's the thing our team most needs hands-on reps with; conceptually it's close to what we already build.
Bridge: A MAF tool is the same idea as a Claude/Copilot skill or tool; MAF speaks MCP, so MCP servers we've already written can be reused as agent tools with little change.

Further reading

  • Agent Framework overview (Microsoft Learn)
  • Introducing MAF (dev blog)
  • If you know AutoGen/SK: migration guide
.NET or Python for Contollo's agents? (Team's agentic experience likely leans Python/TS.) Which MAF version/patterns does the scoped work assume?
ELI5: Foundry is the Azure home for AI. The model catalog lets you pick a model; the Foundry Agent Service is a managed runtime that hosts and scales agents for you — each agent session runs in an isolated sandbox with its own Entra identity and built-in tracing. Think of MAF as how you write the agent, and Foundry as where you run, govern, and observe it. The portal lives at ai.azure.com.

Why it matters here

  • It's the natural place to deploy MAF agents on Azure with identity, observability, and scaling handled.
  • Agents can be published into Microsoft Teams and M365 Copilot — where Contollo's staff already work.
  • Built-in OpenTelemetry tracing and evaluations help with the governance the Semanti report says is pending.
Bridge: Foundry Agent Service is "bring your own framework + model" and is built on the OpenAI Responses API — the same agentic wire protocol many of us already build against.

Further reading

Low-code vs pro-code — the fork for the CMAP agents

Power Platform (via Copilot Studio) is the low-code route; MAF on Azure AI Foundry is the pro-code route. They can coexist, but the choice shapes tooling, skills, and governance.

Our lean: given D55's developer strength and the depth of the CMAP integration, MAF (pro-code) is our working assumption — but Contollo's mention of "Copilot agent workflows" hints they may be picturing Copilot Studio. Worth aligning explicitly.

Copilot Studio

The low-code product for building copilots and agents inside Power Platform (formerly Power Virtual Agents). Relevant because it's the most likely thing Contollo means by "Copilot agents", and it's the main alternative to building the CMAP agents in MAF.

What it is

A maker-focused environment for building conversational agents without writing much code. You define the agent's instructions/topics, give it knowledge sources (SharePoint, websites, files), and wire up actions it performs via Power Automate flows and connectors. Agents publish to channels like Teams, a website, or as extensions of Microsoft 365 Copilot.

Copilot Studio vs MAF

Copilot Studio (low-code)

  • Fast to stand up simple conversational agents.
  • Maker / citizen-developer friendly; less code.
  • Governed via Power Platform + Purview.
  • Best when the agent is mostly Q&A + a few connector actions.

MAF (pro-code)

  • Full control in .NET/Python; complex multi-agent workflows.
  • Fits deep custom integration (e.g. a rich CMAP API).
  • Governed via Azure + Entra + Purview (DSPM for AI).
  • Best when logic/integration outgrows low-code.
Rule of thumb: start in Copilot Studio if the need is a guided Q&A/assistant over existing content; reach for MAF when the agents need bespoke orchestration and tight API/MCP integration — which the CMAP "doing/analyst" split leans towards.

Governed by two layers

  • Power Platform — environments, connector DLP, admin-center controls over who builds/publishes.
  • Microsoft Purview — DSPM for AI, sensitivity labels/DLP on data, and audit over agent interactions.

Governance

How the agent work stays safe, compliant, and auditable. The key idea: governance comes in layers, and which controls apply depends on where the agents are built. This is our chance to turn the report's "pending governance" into a strength.

Governance by platform

Two build routes, two (overlapping) control sets:

Copilot Studio (Power Platform)

  • Power Platform: managed environments, connector DLP, admin center.
  • Purview: DSPM for AI, labels/DLP, audit.

MAF on Azure AI Foundry

  • Azure + Entra: RBAC, PIM, Key Vault, private networking.
  • Foundry: an identity per agent, OpenTelemetry tracing, evaluations.
  • Purview: DSPM for AI over Foundry agents.
Takeaway for the meeting: confirm the build platform early — it decides which governance controls are in play. Purview spans both; the Power Platform controls only apply to Copilot Studio.

Policy & people

  • Acceptable-use policy + approved-tools register (report flags both as pending).
  • Human-in-the-loop review gates on any agent that writes or advises.

Data

  • Sensitivity labels + DLP (Purview) on client-confidential data and PII.
  • Data residency: keep processing in the EU tenancy; verify model regions.
  • Retention decisions on AI tooling (disable, or document risk acceptance).

Identity & secrets

  • Least-privilege via Entra roles + PIM; per-agent identities.
  • Secrets (API keys, CMAP credentials) in Key Vault, never in code.

Visibility

  • Audit + tracing (Purview DSPM for AI, Foundry OpenTelemetry) so every run is explainable.

Governance ↔ risk (from the Semanti report)

  • Shadow-AI leakage (Risk H): acceptable-use policy, approved-tools register, governed gateway, DLP.
  • Liability / PI exposure (Risk G): human-in-the-loop gates, documented verification standards, approved-tools register.
Positioning: lead with governance as the enabler for the agent work, not a blocker — and build on what they have rather than implying their setup is poor.
Confirm current state: any acceptable-use policy, approved-tools register, DLP, or labels today? Purview licensing? These set how much we build vs adopt.

How we might integrate agentic workflows

Four broad routes, roughly in order of directness. The right mix depends on what CMap's API actually allows and what data we're allowed to touch.

  • 1. Direct CMAP API (ideal for agents). If CMap exposes a documented REST API, the "analyst" agent reads (projects, timesheets, utilisation) and the "doing" agent writes (updates, entries) via tools that wrap those endpoints. Cleanest fit for MAF.
  • 2. CMAP MCP server. If CMap (or we) can expose an MCP server over the API, it plugs straight into MAF as a tool set — and lines up exactly with the report's "API/MCP support" wording and our existing MCP experience.
  • 3. Via the Microsoft layer. Where CMap already syncs to Business Central, Power BI, or SQL Server, the analyst agent can read from those instead of CMap directly — often the fastest path to insight without write access.
  • 4. Native connectors for plumbing. Use CMap's built-in connectors for bulk/scheduled data movement (e.g. into Power BI/Fabric) and reserve agent calls for the interactive/decision parts.
Bridge: Routes 1 and 2 are exactly the kind of "wrap an API as tools / stand up an MCP server" work D55 already does well — the new part is the Azure hosting and Contollo's data governance around it.

Access & Onboarding

How Stefan should grant D55 access to Contollo's environment. Because D55 is a separate company, the clean approach splits into two tracks — Azure resources vs the Microsoft 365 / Power Platform side — since they're governed differently. The goal is to ask once, at the right scope, and avoid a drip-feed of permission requests.

Two worlds, two mechanisms

Contollo's estate has two parts that are secured in different ways, so there's no single switch that grants everything:

  • Azure resources (Foundry, Key Vault, Container Apps, storage, monitoring) — governed by Azure Resource Manager (ARM) + Entra roles.
  • Microsoft 365 / Power Platform / Purview / Graph — governed by Entra, M365, and Power Platform admin, not ARM.
Why it matters: the best cross-company tool for the first (Azure Lighthouse) does not reach the second — so we deliberately plan both, rather than discovering the gap mid-build.
ELI5: Azure Lighthouse (delegated resource management) is purpose-built for a service provider in one tenant managing a customer's Azure resources. Contollo delegates a defined scope to D55's tenant once, and we work using our own D55 identities — no per-person guest accounts to manage, no directory-switching.

How it's set up

  • Stefan deploys a small ARM template (or a Managed Services Marketplace offer) once to delegate the scope.
  • Delegate a dedicated subscription or resource group for the engagement — bounds the blast radius.
  • Grant a considered bundle of built-in RBAC roles to a D55 security group at that scope (see the consolidated ask).
  • Use PIM for anything elevated or occasional — just-in-time, not standing admin.

Further reading

  • Azure Lighthouse overview
  • Lighthouse tenants, users & roles
Lighthouse covers Azure (ARM) resources only — it does not reach M365, Power Platform, Purview or Graph. Those are Track 2.
ELI5: These live in Entra/M365, not ARM, so Lighthouse can't project into them. Access here is via guest accounts and an app identity.

How it's set up

  • B2B guest accounts (Entra External ID) for named D55 people, added to a security group — assign roles/licences to the group so adding/removing team members needs no new request.
  • An app registration (or managed identity) for the agents, with admin-consented Graph application permissions granted once — so the CMAP agents authenticate as an app with tightly-scoped permissions, not as a person.
  • Power Platform / Copilot Studio: a dedicated environment + environment role, if that route is chosen.
  • Power BI: a workspace role. Purview: likely read/assess only — their security team owns it.
The agent's app-registration scopes depend on the confirmed first build (which mailboxes/sites it reads). Keep them minimal and expand only if needed.

Tactics to minimise repeat requests

  • Grant at the right scope — one subscription/resource group, not per-resource; new resources inherit access.
  • Assign to a group, not individuals — D55 manages its own team membership without going back to Stefan.
  • Bundle the roles up front — ask once for a considered set rather than discovering gaps one at a time.
  • PIM for the rare elevated action — avoids requesting standing high privilege.
  • Access packages (entitlement management) — optionally wrap the bundle with an expiry + periodic review so onboarding future D55 people is self-service within pre-approved bounds.
