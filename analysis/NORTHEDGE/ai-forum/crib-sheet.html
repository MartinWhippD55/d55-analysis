1. Aligning AI to Business Outcomes

How are leading organisations aligning AI to create tangible business outcomes? What are the most common ways this goes wrong?
  • Data quality is foundational — AI on bad data just produces bad outputs faster
  • Start with the data platform, not the model — clean, catalogued, governed data first
  • MLflow experiment tracking ties models directly to business metrics (revenue, churn, etc.)
  • Goes wrong when: no clear success metric, no feedback loop, or AI is bolted on to broken processes
  • We built a data platform (SageMaker Unified Studio) with catalogued, governed datasets — finance, HR, marketing — before touching any models
  • MLflow experiments log business metrics (£ RMSE, MAPE%) alongside technical metrics — leadership can read them
  • Model Registry creates accountability — who trained it, what data, what version, what performance
  • Common failure: investing in AI product features before the data is clean or engineering org is AI-native

2. Building Customer Confidence & Trust

What have you seen work to build customer confidence and trust in AI? How have regulated businesses overcome resistance?
  • Transparency through observability, not opacity — show what the model does, how it was trained, what data it used
  • Governance conformance packs — automated compliance checks running continuously
  • Model lineage — full traceability from data source → training → deployment
  • Start assistive, prove accuracy, then move to advisory/decision-making

2.1 Governance, Risk & Trust Without Slowing Delivery

  • AWS Config conformance packs for SageMaker — continuous compliance monitoring (encryption, VPC isolation, logging)
  • CloudTrail + Config = full audit trail of who did what, when, to which model
  • Model Monitor detects drift automatically — alerts before bad predictions reach customers
  • EU AI Act: classify use cases by risk tier, apply proportionate governance
  • Ownership model: Engineering owns accuracy, Compliance owns policy, Product owns use case scoping

4. What Separates Real Value from Experimentation?

What separates organisations generating real, scalable value from those stuck in experimentation?
  • Pipelines, not notebooks — if it only runs on a data scientist's laptop, it's not real
  • Automated retraining → evaluation → deployment = production AI, not a prototype
  • Model Registry + versioning = repeatable, auditable, promotable
  • The gap is always operationalisation — going from "it works in a notebook" to "it runs in production unattended"
  • ML Pipeline: data prep → train → evaluate → register → deploy — fully automated, triggered on schedule or data change
  • Model Monitor detects when the model degrades → triggers retraining pipeline → new version auto-deploys if metrics improve
  • Experiment tracking means every run is comparable — no "it worked last Tuesday but I don't know why"
  • Pattern: experimentation orgs have notebooks, production orgs have pipelines

5. Competitive Race or Structural Shift?

Are we in a competitive race, or a slower structural shift? How should that change pace and type of investment?
  • Both — structural shift in tooling, competitive race in adoption speed
  • The tools are commoditising fast (everyone has access to Claude, GPT, Bedrock)
  • The advantage is in data + execution speed — proprietary data + AI-native teams
  • Clarity of intent is the performance multiplier — applies at every level, not just technical. Clear specs, clear strategy, clear communication. AI amplifies clarity and punishes ambiguity.
  • Cost is trivial: ~$100/seat/month. The real cost is delay.
$100/seat/month for 5x productivity. For 65 devs: ~$80k/year in tooling vs millions in equivalent headcount — or streamline headcount for a net saving.
  • Long-term costs: inference is getting cheaper every quarter. Training costs are one-off. Tooling is subscription.
  • Prioritisation: start with developer productivity (immediate ROI), then internal process automation, then customer-facing AI features
  • For Cezanne specifically: AI-native engineering org is a valuation multiplier at exit

6. What Does "Good" Look Like at Scale?

What does "good" look like when AI is truly embedded — operating model, talent, culture? Key inflection points?
  • 65 devs producing output of 200-325 (5x, improving)
  • Release cadence in days, not months
  • AI embedded in the product AND the process of building the product
  • Inflection point: when the bottleneck shifts from building to specifying

6.1 High-Performing AI-Enabled Product Org

  • Central AI platform team (data + infra) + embedded AI practitioners in squads
  • From experimentation to scale: prove in one squad → document patterns → roll out with playbooks
  • Biggest productivity gains: code generation, test automation, documentation, data transformation
  • Common failure: treating AI as a separate initiative instead of embedding in existing workflows

6.2 AI-First Product Development Lifecycle

  • More time in analysis & design, less in implementation — specs become the bottleneck/multiplier
  • Engineering & architectural best practices matter MORE with AI — not less
  • Contracts & integration points defined upfront
  • Implementation with agentic tooling against well-defined specs
  • Not waterfall — it's recognising that garbage specs at 5x speed = garbage 5x faster
  • Our lifecycle: Analysis → Contracts/APIs → Implementation (AI-assisted) → Testing (human-in-loop + automated) → Documentation (AI-generated)
  • Standardise prompts: skills/playbooks that capture "how we do X" as reusable AI instructions
  • Tooling: Copilot + Claude in IDE, MCP servers for Jira/GitHub/DB access, Playwright for regression testing
  • Quality control: PR review agents that reference requirements and acceptance criteria automatically

6.3 Preventing Product Becoming a Bottleneck

  • When devs go 5x faster, POs, BAs, PMs become the constraint — the "middle layer"
  • AI can reduce dependency on PMs: auto-generated specs from requirements, AI-assisted prioritisation
  • Guardrails that enable speed: clear contracts, automated testing, CI/CD gates — not approval committees
  • On our project: primary resistance came from POs/BAs/Programme Managers — coordination roles couldn't keep pace
  • Unblocked by: action first, metrics to prove it, regular retros, 1-on-1 training
  • Four Fears Framework: Controllers (loss of control), Stabilisers (hierarchy disruption) — address directly
  • Not everyone comes around — plan for it, budget time for it

6.4 AI Architecture & Operating Model

  • Emerging patterns: RAG for knowledge retrieval, agentic systems for multi-step tasks, structured outputs for reliability
  • Most common mistake: over-engineering — start simple (prompt engineering + RAG), graduate to fine-tuning only when needed
  • Human-in-the-loop: adds value at decision points, slows things down at implementation points
  • Vendor strategy: abstract the model layer, swap providers without rewriting the application
  • Pattern: prompt engineering first → structured outputs → tools/RAG → fine-tuning (last resort, highest cost)
  • Agentic mistakes: unbounded autonomy, no eval framework, no fallback to human
  • Open-source vs commercial: evaluate on eval quality and observability, not just cost
  • TTS: depends on use case — ElevenLabs for quality, AWS Polly for cost/scale

6.5 Evaluation, Guardrails & Governance at Scale

  • Evals: offline (benchmark datasets) + online (production monitoring) — both required
  • Making evals reliable for CI: pin model versions, use deterministic settings (temp=0), statistical thresholds not pass/fail
  • Guardrails: input validation, output filtering, confidence thresholds, human escalation paths
  • Model Monitor for drift detection — automated, continuous, alerts on threshold breach
  • Conformance packs for infrastructure compliance — runs continuously, flags non-compliance
  • Fine-tuned models in regulated domains: version everything, test on held-out regulatory scenarios, maintain rollback capability
Model Dashboard → drift monitoring + conformance pack results

6.6 Memory, Personalisation & Context Management

  • Pattern: vector store + structured profile + RAG (hybrid approach)
  • User vs org context: separate stores, separate access controls, never cross-contaminate
  • Memory lifecycle: decay old context, summarise long histories, re-evaluate periodically
  • Risk: personalisation that creates filter bubbles or leaks data between tenants
  • For Cezanne (multi-tenant HR SaaS): strict tenant isolation is non-negotiable — vector store per org, not shared
  • Summarisation for long employee histories — don't stuff 10 years of records into context
  • Pattern: structured profile (role, permissions, preferences) + RAG for relevant docs + short-term conversation memory

6.7 Measuring Real AI Impact

  • Measure outcomes, not usage — "200 developers using Copilot" means nothing if velocity hasn't changed
  • Leading indicators: cycle time, deployment frequency, defect rate, time-to-first-commit
  • Lagging indicators: revenue per engineer, cost per feature, customer satisfaction
  • Trap: measuring "AI adoption %" instead of business impact
  • On our project: tracked PRs/week, lines changed, story points delivered — before/after AI tooling
  • MLflow tracks model performance metrics over time — tie to business KPIs (forecast accuracy → revenue confidence)
  • For PE: the metric that matters is output per £ of engineering cost — that's the valuation lever

7. Source of Competitive Advantage

Where is the real advantage — tools, data, or teams? How might that change?
  • Tools: commoditising fast — everyone has access, no moat
  • Data: proprietary, clean, governed data is the real moat — especially in HR/payroll
  • Teams: AI-native engineering culture is hard to copy and compounds over time
  • For Cezanne: 15+ years of HR/payroll data across thousands of orgs = massive competitive asset IF governed properly
  • Priority use cases for Cezanne: compliance automation (regulation changes → auto-update policies), document generation (contracts, letters), employee self-service (natural language queries over HR data)
  • Trade-off: AI innovation vs core roadmap — start with AI that accelerates existing roadmap delivery, then add AI product features
  • What failure looks like: 12 months of "AI strategy" with no shipped features, talent attrition, competitors moving faster
