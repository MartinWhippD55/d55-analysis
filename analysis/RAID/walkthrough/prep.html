How to think about the estimate

An estimate is only as good as our understanding of scope, complexity, and unknowns. The walkthrough exists to shrink the unknowns enough that we can put a credible range (with stated assumptions) against each deliverable. We're not trying to leave with a number — we're trying to leave able to produce one.

  • Estimate in ranges, not points — e.g. t-shirt sizes or low/high day bands, each tied to explicit assumptions.
  • Every "to investigate" that stays open becomes an assumption — and a risk line in the estimate.
  • Separate "get to a working v1" from "the full build" — lets us give a smaller, faster first number.

The must-see checklist

If we get through the walkthrough with these captured, we can estimate. Prioritise them if time runs short.

  • The code & a live run — see the repo(s) and watch a real agent run end to end, so we understand the LangGraph shape and where to instrument.
  • Current AWS account picture — single vs multi-account, what's already deployed, and how (console-clicked vs IaC).
  • What exists vs. greenfield — any current logging, metrics, "central DB", CI/CD, IaC, secrets handling. We estimate the gap, not the whole thing.
  • Data residency & sensitivity ruling — the one answer that decides LangSmith vs AWS-only, which swings the observability estimate the most.
  • Scale & volume — runs/day now and projected; drives DB, hosting, and storage sizing.

Their stack

ELI5: LangGraph is a way to build AI "agents" as a flowchart. Each box (node) does a step — call the model, use a tool, check a result — and the arrows decide what happens next. It keeps track of state as the agent works through the graph, and can loop, branch, or pause for a human. Think of it as the wiring diagram that turns a single LLM call into a multi-step assistant.

Why it matters here

  • An "agent run" = one trip through the graph. That run is exactly what we need to observe and measure.
  • LangGraph has built-in hooks (callbacks, checkpoints) we can tap for metrics without rewriting agent logic.
  • It's from the LangChain team, so the default observability path is LangSmith (a SaaS) — relevant to the AWS/data-residency question.

  • Persistence & checkpoints

Engagement areas

ELI5: "Observability" is being able to answer what happened and why after the fact, from the data the system emits. For an AI agent that means: how long did the run take, how many model/tool calls, how many tokens, what did it cost, did it succeed, where did it get stuck. A "trace" stitches those steps into one timeline you can replay.

Why it matters here

  • This is the primary deliverable: capture agent metrics into a central DB for analysis and impact visibility.
  • Key tension: LangGraph's native tool is LangSmith (SaaS), but the client wants AWS-first / data residency. OpenTelemetry is the vendor-neutral alternative that can send data to AWS.

Further reading

AWS Account Setup & Security Posture

As a security firm, CovertSwarm will judge us on how we secure their cloud, not just how we ship features. This tab is our checklist of the account-structure and security services we'd expect to assess and stand up — with plain-English sound bites we can drop into the conversation.

Foundations — account structure & identity

Sound bite: "Rather than one big AWS account, we'd use multiple accounts — separating prod, test, logging and security — under a single Organization. Control Tower sets that up with sensible guardrails baked in from day one."

Why it matters here

  • A multi-account "landing zone" is the modern baseline; it isolates blast radius (a compromise in test can't touch prod).
  • Enables org-wide guardrails (Service Control Policies) and centralised logging/billing — feeds the "multiple environments" deliverable.

Further reading

  • AWS Organizations
  • AWS Control Tower
Single account or already multi-account? Any existing Organization / SCPs / landing zone we must fit into?
Sound bite: "Nobody logs in with long-lived IAM users. Identity Center gives each person single sign-on with short-lived, role-based access across all accounts — ideally wired to their existing identity provider."

Why it matters here

  • Kills the biggest common finding: shared/long-lived credentials. Access becomes temporary and auditable.
  • Central place to grant/revoke people across every account — clean joiner/mover/leaver story.
  • Pairs with MFA enforcement — table stakes for a security client.

Further reading

  • IAM Identity Center
Do they have an IdP (Okta / Entra ID / Google)? Any IAM users with access keys we should retire? MFA enforced everywhere?
Sound bite: "Every service and person gets only the permissions they actually need — nothing broad or wildcard. Apps assume roles rather than holding keys."

Why it matters here

  • Least privilege is the single most-cited AWS security principle and the first thing a pentester probes.
  • The Python agents should run under narrowly-scoped task roles, not embedded credentials.

Further reading

  • IAM best practices
  • IAM Access Analyzer (policy generation)
Any over-permissive roles / wildcard policies today? Where are workload credentials sourced from?
